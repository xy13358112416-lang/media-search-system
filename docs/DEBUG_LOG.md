## DBG-001　非法文件类型提示前界面长时间未响应

日期为 2026-11-12。状态为已在本地工作区修复并通过控件自动复测；未提交。正式结果见末尾“DBG-001 / DBG-011 正式修复与复测”，以下保留原始排查证据。

### 版本和环境

- 本地提交为 `c6dddf2`，已整合 `fix/qt-dropdown-style` 和扩充数据。
- Windows，Qt 6.8.3，配套 MinGW 13.1。
- 数据为扩充 CSV 的独立临时副本，共 530 条，原始文件和用户运行数据均未修改。
- 完整项目和业务库使用 Release 构建。诊断程序包含同版本的 Qt 界面源码，使用编译器默认优化设置，通过 offscreen 平台分段计时。

### 现象和复现

在新增窗口输入有效日期及非负数值，文件类型填写不受支持的 `213`，点击保存。用户观察到窗口显示“未响应”，等待后才返回错误提示。预期应快速提示输入不合法，原有记录保持完整。

### 排查过程

1. 检查新增调用链，发现类型校验失败后仍会进入 `recoverAfterError()`。
2. 此函数先重新加载 CSV 和索引，再调用 `refreshTypes()`，最终重新填充整张表格，然后显示错误提示。
3. 分别测量非法新增请求、重载、窗口初始化和重复刷新，区分业务耗时与界面耗时。
4. 在临时诊断程序中将表头列宽模式改为固定，再执行相同的重复刷新，作为原因验证对照。

### 实测结果

| 操作 | 本次耗时 |
|---|---:|
| 初次加载 530 条记录 | 27 ms |
| 非法新增请求，三次 | 30、34、33 ms |
| 失败后的重新加载 | 14 ms |
| 窗口构造 | 35 ms |
| 首次显示及事件处理 | 23 ms |
| 自动列宽模式下重复填表，三次 | 10643、9792、14536 ms |
| 上述三次填表后的事件处理 | 2、1、2 ms |
| 临时固定列宽后重复填表 | 2 ms |
| 固定列宽填表后的事件处理 | 3 ms |

以上是本机诊断实验，不能直接当作正式程序在所有 Windows 环境中的响应时间。固定列宽对照只运行了一次，后续正式修复应增加重复测量。

### 已确认的原因

业务类型校验能快速返回。主要耗时位于已有内容的表格被逐个替换单元格时，按内容计算列宽带来了大量重复布局工作。固定列宽的对照使填表耗时显著下降，支持该原因判断。

这段填表逻辑在界面线程同步执行，执行期间无法及时处理窗口消息，与用户观察到的“未响应、最终恢复”现象吻合。此结论来自分段计时和列宽模式对照，未使用性能分析器统计每个 Qt 内部函数的调用次数。

### 正式修复建议

- Qt 模块在批量替换单元格期间暂停自动列宽计算，完成后统一计算一次，或采用合适的固定列宽。
- 对明确未写入数据的输入校验错误，直接返回提示，避免整库重载和整表刷新。
- 保存可能已完成、索引更新失败等情况仍需恢复逻辑，不能简单删除所有失败恢复操作。
- 主逻辑可在读库和预留编号之前校验记录，Qt 同时提供输入引导，保留后端校验。

### 补充对照：成功新增为何可能不卡

用户补充观察到格式正确、保存成功时没有明显卡顿。随后在相同版本、530 条临时副本和 offscreen 诊断方式下，依次比较失败恢复、成功新增和成功删除。

| 本次操作 | 业务阶段 | 表格行数变化 | 填表耗时 | 含随后事件处理 |
|---|---:|---|---:|---:|
| 非法类型新增后的恢复 | 新增失败 11 ms，重新加载 4 ms | 530 → 530 | 6171 ms | 6172 ms |
| 合法新增成功后的刷新 | 新增成功 18 ms | 530 → 531 | 4 ms | 5 ms |
| 合法删除成功后的刷新 | 未单独计时 | 531 → 530 | 4 ms | 5 ms |

结论需要细化为：成功和失败恢复都会调用重填表格的代码，但两条路径的实际耗时差别很大。本次异常恢复行数不变，耗时达到秒级；成功增删改变行数，同一填表路径只需数毫秒。不能笼统表述为“每次全表刷新都会卡”。

该对照直接触发类型筛选控件的刷新信号，以进入同一填表路径；业务阶段单独调用对应接口。数据来自独立临时副本，未修改用户媒体库。这些数字不包含用户填写表单和确认提示的时间。Qt 内部为何在两种行数状态下采取不同布局处理，尚未用函数级性能分析确认。

补充诊断程序位于仓库外的 `.qt-sdk/test-temp/qt-rowcount-*` 临时目录。此前固定列宽对照和本次行数变化对照共同缩小了问题范围，正式修复时必须同时回归成功与失败路径。

### 函数级计数：原地刷新慢的具体机制

同日继续使用 Qt 6.8.3 官方源码核对调用链。在仓库外诊断程序中派生表格和单元格委托，分别统计 `dataChanged()`、`sizeHintForColumn()` 和委托 `sizeHint()` 的次数。诊断程序以 `-O2` 编译，使用同版本界面源码、Release 业务库及 offscreen 平台，数据仍为独立临时副本。

| 场景 | 行数 | 同步刷新 / 含事件处理 | dataChanged 次数 | 列宽扫描次数 | 单元格尺寸计算次数 |
|---|---|---|---:|---:|---:|
| 普通原地刷新 | 530 → 530 | 6627 / 6629 ms | 2120 | 6360 | 3370800 |
| 新增一条后刷新 | 530 → 531 | 4 / 5 ms | 2124 | 3 | 1593 |
| 原地刷新前显式安排延迟布局 | 531 → 531 | 4 / 5 ms | 2124 | 3 | 1593 |
| 临时固定列宽后原地刷新 | 531 → 531 | 0 / 1 ms | 2124 | 0 | 0 |

普通原地刷新中，`dataChanged()` 累计耗时约 6622.28 ms，其中列宽扫描累计耗时约 6582.20 ms。这两个累计区间有嵌套关系，不能相加。新增一条时，`dataChanged()` 累计耗时约 0.0552 ms；显式延迟布局时约 0.0746 ms。

源码调用链和计数共同支持以下结论。

1. `QTableModel::setRowCount()` 在新旧行数相等时直接返回。行数改变则执行插入或删除，触发表格的 `rowCountChanged()`，后者安排延迟布局。
2. 项目每次刷新都会新建并替换四列的单元格对象。即使文字相同，`QTableModel::setItem()` 仍发出 `dataChanged()`。530 行因此产生 2120 次数据变更通知。
3. `QHeaderView::dataChanged()` 将自动列宽标记为需要重新计算。没有待处理延迟布局时，`QAbstractItemView::dataChanged()` 会立即请求更新单元格区域。
4. 确定更新区域需要调用 `QTableView::visualRect()`，读取列位置和列宽；`QHeaderView::sectionPosition()`、`sectionSize()` 会执行尚未完成的尺寸调整。于是尚未批量填完，就开始扫描已有内容计算列宽。
5. 本项目有三列使用 `ResizeToContents`，每次扫描在 530 行数据上测量该列的全部 530 个单元格。本次计数正好对应 `2120 × 3 = 6360` 次列宽扫描，以及 `6360 × 530 = 3370800` 次单元格尺寸计算。
6. 行数变化带来的延迟布局，使 `dataChanged()` 跳过逐格请求更新区域。批量填完后再统一处理，计数降为三列各扫描一次。显式安排延迟布局也能让行数不变的刷新走快路径，进一步验证了差异来自布局状态。

现有 `QSignalBlocker(table_)` 主要阻止表格自身对外发信号；数据模型仍会发出 `dataChanged()`，表头和视图仍会处理它，因而没有消除该耗时链。

这些对照是探针内的单轮实验，说明调用机制和耗时分布。单元格扫描量还受 Qt 的列宽扫描精度配置影响，不能把当前公式无条件推广到任意更大数据规模。

本次探针位于仓库外的 `.qt-sdk/test-temp/qt-layout-trace-1bc34125e2d44919a7cdd8bd088dc969/probe.cpp`。项目 Qt 源码未修改。复核使用的官方源码为以下文件中的上述函数。

- https://github.com/qt/qtbase/blob/v6.8.3/src/widgets/itemviews/qtablewidget.cpp
- https://github.com/qt/qtbase/blob/v6.8.3/src/widgets/itemviews/qabstractitemview.cpp
- https://github.com/qt/qtbase/blob/v6.8.3/src/widgets/itemviews/qheaderview.cpp

## DBG-001 补充：真实保存按钮的失败调用链

同日根据用户追问，直接追踪“媒体 CSV 没有改变，为什么仍然整表刷新”。本轮在临时复制的界面源码中插入阶段日志，程序化打开实际新增对话框、填写字段并点击其保存按钮，走实际 `accepted` 回调和错误弹窗路径。自动关闭诊断副本的弹窗和表单以结束测试。原项目界面源码未修改，输入数据为独立的 530 条临时副本。

本次输入文件名 `2212`、文件类型 `213`、大小和浏览次数为 `0`，日期为有效的 `2026-11-30`。探针以 `-O2` 编译，Qt 平台为 offscreen。

```text
TRACE 0 ms click Save
TRACE 0 ms calling addNew
TRACE 11 ms addNew FAILED
TRACE 11 ms recovery load BEGIN
TRACE 15 ms recovery load END
TRACE 15 ms recovery refresh BEGIN
TRACE 15 ms setRowCount BEGIN
TRACE 15 ms setRowCount END
TRACE 15 ms replacing cells BEGIN
TRACE 5935 ms replacing cells END
TRACE 5935 ms recovery refresh END
TRACE 5939 ms entering error message exec
TRACE 5940 ms error dialog reached
TRACE 5942 ms add dialog returned
RESULT error_seen=1 media_csv_unchanged=1 record_count=530
```

探针对媒体 CSV 的操作前后 SHA-256 进行比较，确认文件字节没有改变，记录数仍为 530。日志确认先执行了整表刷新，再出现类型错误提示。

直接原因是新增回调对任意 `result.success == false` 都调用 `recoverAfterError()`。后者无条件执行 `library_.load()` 和 `refreshTypes()`，没有区分“输入校验失败、媒体记录没有写入”与“已经写入但索引更新失败、确实需要恢复”。原意是处理可能部分成功的保存，但调用范围过宽。

界面仅先检查类型非空和不含点，`213` 因而进入主逻辑。主逻辑在 `CsvMediaRepository::add()` 才拒绝不支持的类型，此前已经读库并预留编号。媒体 CSV 未变不等于编号状态文件也未变，此处的哈希比较只针对媒体 CSV。

修复应把支持类型等确定性校验前置，并按失败阶段决定是否需要重新加载和刷新。输入错误应保留表单、直接提示。对于可能已经持久化的异常，保留恢复能力。表格批量布局的性能问题仍应单独修复，避免其他合法刷新场景再次触发。

本轮探针和原始日志保存在仓库外的 `.qt-sdk/test-temp/invalid-save-trace-*` 目录，分别为 `probe.cpp`、`instrumented_frontend.cpp` 和 `trace.log`。

## DBG-011　媒体库和检索页之间切换卡顿

原始诊断日期为 2026-11-12，提交为 `c6dddf2`。状态为已在本地工作区修复并通过控件自动复测；未提交。正式结果见末尾“DBG-001 / DBG-011 正式修复与复测”。关联问题为 DBG-001，共享同一表格批量布局瓶颈。

### 复现及测量方法

使用 30 条原始样例和 530 条扩充样例的独立临时副本。正常加载 `MediaLibrary`，创建实际的 `LibraryWindow` 并处理首次显示事件。通过 `QTabBar::setCurrentIndex()` 触发生产代码的 `currentChanged` 回调，未输入检索条件，记录切页回调的同步耗时、处理事件后的总耗时，以及表格数据通知、列宽扫描和单元格尺寸计算次数。

环境沿用 Windows、Qt 6.8.3、配套 MinGW 13.1。探针以 `-O2` 编译，业务库为 Release，Qt 使用 offscreen 平台。每个场景本轮测量一次，不能当作所有机器上的响应时间或统计分位数。

### 实测结果

| 数据量 | 操作 | 同步 / 含事件处理 | 列宽扫描次数 | 单元格尺寸计算次数 |
|---:|---|---|---:|---:|
| 30 | 媒体库 → 检索 | 21 / 23 ms | 360 | 10800 |
| 30 | 检索 → 媒体库 | 21 / 23 ms | 360 | 10800 |
| 530 | 媒体库 → 检索 | 5884 / 5885 ms | 6360 | 3370800 |
| 530 | 检索 → 媒体库 | 5857 / 5859 ms | 6360 | 3370800 |
| 530 | 临时安排延迟布局后，媒体库 → 检索 | 4 / 5 ms | 3 | 1590 |
| 530 | 检索 → 推荐 | 3 / 5 ms | 12 | 1635 |
| 530 | 推荐 → 检索 | 4 / 11 ms | 12 | 4785 |
| 530 | 临时固定列宽后，检索 → 媒体库 | 1 / 2 ms | 0 | 0 |

530 条媒体库切检索时，`sizeHintForColumn()` 内累计耗时约 5842.06 ms，几乎覆盖同步切页耗时。两条慢路径均收到 2120 次 `dataChanged()`。

原始日志中的 `empty_search_ms` 字段在输出前还调用了一次 `library.records()`，因此包含空条件检索和读取排序后记录的额外开销，不能当作纯检索计时。本轮分别约 0.03 ms 和 0.1925 ms，仅用于确认该组合基准没有秒级耗时。

### 原因分析

1. 切换到检索时，页签回调无条件调用 `showSearchResults()`。空条件检索仍返回全部记录，随后调用 `populateTable()`。
2. 全部媒体显示 530 行，空条件检索也显示 530 行，`setRowCount(530)` 因而直接返回，未触发行数变化对应的延迟布局。
3. 代码仍逐格创建并替换 2120 个单元格，触发了 DBG-001 已验证的重复自动列宽扫描。
4. 切回媒体库时，回调调用 `refresh()`，同样重填 530 行，因此出现相同瓶颈。
5. 推荐通常只显示 5 行，切换涉及行数变化，因而本次对照较快。不能据此认定所有推荐切换在任意数据状态下都不会慢。

这次没有新增或保存媒体记录，说明卡顿可以独立于失败恢复流程发生。需要修复共享的 `populateTable()`，不能仅修改新增错误提示路径。

### 修复建议和验收范围

- 批量填表期间暂停自动尺寸计算，结束后统一布局，或使用合适的固定/交互列宽。
- 可以对数据和查询条件均未变化的场景减少重复填充，但要保证保存、删除、筛选条件及检索条件变化后及时更新。
- 修复后覆盖双向切页、空条件检索、相同结果数的不同查询、清空条件、筛选切换、推荐切换和新增失败恢复。
- 保持列表记录、命中数量和详情一致，在同一环境下记录多次响应耗时。

## DBG-001 / DBG-011 正式修复与复测

### 实施内容与顺序

1. 先加入回归测试并运行旧代码。30 条记录的切页产生 360 次列宽扫描，超过固定工作量上界；非法类型保存的新增业务入口调用为 1，预期为 0。两项检查均按预期失败，原始结果保存在 `DBG-001-011-regressions-before.txt`。
2. 单独修改共享 `populateTable()`：保存每列原来的布局模式及绘制开关，批量填表期间将列模式临时设为 Fixed 并关闭重绘，用 qScopeGuard 在退出时恢复，让 Qt 统一处理自动列宽。空结果的提前返回同样恢复。原有 Stretch / ResizeToContents 模式、详情和选中记录保留，不增加结果缓存。
3. 单独验证这一步，530 条记录每次切页降为 3 次列宽扫描、1590 次尺寸计算。五轮中位数媒体库→检索为 19.7279 ms，检索→媒体库为 18.3466 ms。此时非法类型提示虽降到 46.6219 ms，但仍有新增 1 次、重载 1 次及整表 2120 次数据通知，编号状态文件仍会改变。这是布局优化有效但多余恢复流程尚未消除的中间证据。
4. 再修改新增保存回调：类型 trim / toUpper 后，使用已有 `MediaLibrary::supportedFileTypes()` 进行白名单检查。不支持时直接提示、保留表单并定位类型字段，在调用 `addNew()` 前返回。业务校验和其他异常的原恢复流程保留，公开接口、CSV 格式及检索算法未改动。
5. 完整构建、运行原有测试及新增界面回归，重跑五轮性能测量；只读代码复核未发现需修复的问题。

Windows 11，Qt 6.8.3，配套 MinGW 13.1；项目、测试与性能目标均由同一 CMake Release 配置构建（GCC `-O3 -DNDEBUG`）。在生产修改前保留独立基线可执行文件，再构建中间版本和最终版本，使用相同探针源码与控件样式。业务与检索库未改。

所有测量均为 offscreen 模式，使用 30 / 530 条种子 CSV 的独立临时副本。每个数据规模、每个方向和非法保存均记录 5 次。切页总耗时包含回调、已投递布局事件、表头尺寸请求和事件处理；非法保存计时为点击保存到进入错误对话框事件循环，不含人工等待。

本轮基线比前文早期单轮诊断慢；二者诊断程序与构建方式不同，不混算统计结果，不把 5.9 秒旧诊断值当成本轮修复前值。绝对时间受平台、字体和系统负载影响；扫描次数变化为更直接的根因证据。offscreen 的字体目录缺失与 `propagateSizeHints` 提示原样保存在日志中，不能据此判断正常窗口的字体或外观。
