# 人物数据表迁移草案

此变更只定义服务器同一份 SQLite 数据库内的人物表和迁移，不提供人物读写 RPC、资讯抓取或历史事件快照写入。表结构及版本号需要与正在制定的 N00 仓储边界共同审查；草案未合并前，不应把它当作已经确认的公共协议。

`WarehouseServer::openDatabase` 在现有初始化事务中执行 `person_schema::migrate`：从版本 1 创建版本 2 的人物表并登记版本；任何步骤失败由调用方回滚。已经是版本 2 时检查字段、类型、主外键、索引及必要 CHECK 片段；CHECK 检查不是完整 SQL 语义分析。不支持的后续版本、结构不匹配或未开启外键时明确失败。之后修改表结构必须使用新的迁移版本，不直接修改版本 2 的既有定义。迁移不从旧姓名字段推断人物 ID，也不改动媒体、账号、历史或反馈内容。

| 表 | 保存的内容 |
|---|---|
| `person_catalog`、`person_aliases` | 已确认的稳定人物 ID、显示名、身份来源和别名；相同姓名不能自动合并 |
| `person_credits` | 人物 ID、服务端作品 ID、角色及对应来源；每个角色独立记录 |
| `person_follows` | 用户自己的关注，以及关注时已知的最小姓名/角色快照；作品失效后可供后续仓储实现安全取关 |
| `person_sources`、`person_updates` | 已配置资讯源和有来源的缓存记录；`feed_url` 对应已配置来源，`source_url` 是具体文章地址，两者可以不同。未知日期可以为空，失败可标记 stale，不伪造抓取时间 |
| `person_history_snapshots` | 每条浏览事件当时已确认的人物角色快照；外键随用户清理行为记录级联删除 |

数据库连接仍由服务器持有，迁移函数不创建连接、不自行提交。后续 N03 仓储负责校验身份、HTTPS 来源、内容、时间和权限；Qt 的服务端查询与资讯 provider 通过仓储接口访问，不直接创建另一份数据库。已经存在的旧浏览不会自动获得人物快照，后续快照接线必须区分旧数据缺失和确实没有人物。

自动测试覆盖旧用户/行为保留、重复迁移、表名与索引冲突时回滚、外键关闭、未知及超大版本号、已有版本 2 结构被改动；还需与实际 Qt 端确定的 N00 接口共同验收。
